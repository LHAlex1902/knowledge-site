1 📖 JMeter 是什么？

JMeter 是 Apache 基金会的开源性能测试工具，纯 Java 开发。核心能力是模拟大量用户并发请求目标服务器，测量响应时间、吞吐量、错误率等性能指标。

💡 一句话： JMeter = 虚拟用户模拟器。设置"1000 个用户同时登录"，观察服务器扛不扛得住。
特性说明
协议支持HTTP/HTTPS、WebSocket、FTP、JDBC（数据库）、JMS、TCP/UDP 等
运行模式GUI（图形界面拖拽）+ CLI（命令行，适合 CI）
分布式支持多台机器联合压测（分布式模式）
插件生态大量插件扩展功能（HTML 报告、监控、高级图表等）
跨平台Windows / macOS / Linux 均可运行（需 Java 8+）

JMeter vs pytest+requests

维度JMeterpytest + requests
定位性能/压力测试功能/接口测试
并发原生支持高并发（线程组）需 pytest-xdist 并行
操作方式GUI 拖拽配置写 Python 代码
报告内置聚合报告、图表需 pytest-html / allure
CI 集成CLI 模式天然适合 CI
学习曲线上手快，精通难需 Python 基础

两者互补：pytest 做日常功能测试，JMeter 做版本上线前的压力测试。

组件作用类比
线程组 (Thread Group)控制并发用户数、启动时间、循环次数控制"来多少玩家、多快来、玩几轮"
取样器 (Sampler)发送 HTTP/FTP/JDBC 等请求玩家点击按钮发出的请求
断言 (Assertion)校验响应是否正确检查页面有没有报错、数据对不对
监听器 (Listener)聚合报告、图表、查看结果树压测后的性能报告
配置元件 (Config Element)CSV 数据、HTTP 头、Cookie、缓存每个玩家的登录账号、请求头

其他重要概念

概念说明
前置处理器请求发送前执行（如提取变量、加签）
后置处理器请求返回后执行（如提取响应中的 token）
逻辑控制器控制请求执行顺序（循环、条件、并行等）
变量存储数据，在请求中用 ${变量名} 引用

4 🗺️ 测试计划结构 — 从空白到第一个压测

4.1 创建测试计划

  • 添加线程组

    右键「测试计划」→ 添加 → 线程(组) → HTTP 请求的线程组

    设置：线程数=10（10 个并发用户），循环次数=5（每个用户执行 5 轮）

  • 添加 HTTP 请求

    右键「线程组」→ 添加 → 取样器 → HTTP 请求

    填写：协议=http，服务器=example.com，端口=80，路径=/

  • 添加监听器

    右键「线程组」→ 添加 → 监听器 → 聚合报告

  • 运行

    点击顶部绿色 ▶ 按钮，或按 Ctrl+R

    • 4.2 标准测试计划结构

    Java测试计划树形结构
    测试计划 (Test Plan)
├── HTTP 请求默认值        # 配置元件：公共的服务器地址、端口等
├── 线程组 (Thread Group)
│   ├── HTTP 头管理器      # 配置元件：公共请求头
│   ├── CSV 数据文件设置   # 配置元件：参数化数据
│   ├── 登录请求           # 取样器
│   │   ├── JSON 提取器    # 后置处理器：提取 token
│   │   └── 响应断言       # 断言：校验登录成功
│   ├── 获取用户信息       # 取样器
│   └── 查询列表           # 取样器
├── 聚合报告               # 监听器
└── 查看结果树             # 监听器（调试用）
    💡 层级规则：
    • 配置元件放在线程组下 → 该线程组内所有请求共享
    • 监听器放在线程组下 → 只统计该线程组的数据
    • 监听器放在测试计划下 → 统计所有线程组的数据

    5 🌐 HTTP 请求配置详解

    5.1 GET 请求

    JavaGET 请求配置
    # HTTP 请求配置：
协议:     http
服务器:   api.example.com
端口:     8080
方法:     GET
路径:     /api/users?page=1&size=20

# 或者把参数拆到「参数」标签页：
参数:
  page  = 1
  size  = 20

    5.2 POST JSON 请求

    JavaPOST JSON 配置
    # HTTP 请求配置：
方法:     POST
路径:     /api/users
Body Data:
{
  "username": "testuser",
  "password": "123456"
}

# 同时添加 HTTP 头管理器：
Content-Type: application/json

    5.3 提取响应数据（后置处理器）

    JavaJSON 提取器 — 提取 token
    # 添加后置处理器 → JSON 提取器
JSON 路径:    $.data.token
变量名:       token

# 后续请求中用 ${token} 引用
# HTTP 头: Authorization = Bearer ${token}
    ⚠️ 常见坑：
    • POST 请求 Body Data 写 JSON 时，必须加 HTTP 头管理器设置 Content-Type: application/json
    • 变量引用用 ${变量名}，不是 %变量名%
    • 提取器只对成功的响应生效，失败时提取不到数据

    6 📊 参数化 — CSV 数据驱动

    压测时不能每次都用相同数据（比如同一个账号登录），需要从 CSV 文件读取不同数据模拟不同用户。

    6.1 准备 CSV 文件

    Javatest_users.csv
    username,password,expected_role
user001,pass123,admin
user002,pass456,user
user003,pass789,user
user004,pass000,vip
user005,pass111,user

    6.2 配置 CSV 数据文件

    JavaCSV 数据文件设置
    # 添加配置元件 → CSV 数据文件设置
文件名:              test_users.csv
文件编码:            UTF-8
变量:                username,password,expected_role
忽略首行:            True      # 跳过表头
遇到文件结束符时:    重新循环  # 数据用完从头再来

    6.3 在请求中使用

    Java登录请求中使用变量
    # Body Data：
{
  "username": "${username}",
  "password": "${password}"
}

# 断言中也可以引用：
# 响应断言 → 模式匹配规则 → 包含 ${expected_role}
    💡 参数化要点：
    • CSV 文件路径相对于 JMeter 启动目录（bin 目录）
    • 线程数 > CSV 行数时，默认「重新循环」会复用数据
    • 多个线程同时读 CSV 时，每行数据只被一个线程读取（独占）

    7 ✅ 断言 — 校验响应正确性

    断言用来判断响应是否符合预期。没有断言的压测只是"发请求"，加了断言才是"测试"。

    断言类型用途示例
    响应断言校验响应文本/状态码包含 "success"、状态码 200
    JSON 断言校验 JSON 结构$.data.token 不为空
    响应时间断言校验响应时间响应时间 < 2000ms
    大小断言校验响应大小响应大小 > 100 字节
    XML 断言校验 XML 结构包含 <result> 标签

    常用断言配置

    Java响应断言配置
    # 断言1：状态码 = 200
响应断言:
  响应字段: 状态码
  模式匹配规则: 等于
  模式: 200

# 断言2：响应包含 "success"
响应断言:
  响应字段: 文本响应
  模式匹配规则: 包含
  模式: success

# 断言3：响应时间 < 2秒
响应时间断言:
  响应时间(毫秒): 2000
    ⚠️ 注意： 断言失败不会中断测试，请求会继续执行。断言失败只会在监听器中标记为红色。

    8 📈 监听器 — 生成性能报告

    监听器用途推荐度
    聚合报告按请求名汇总：样本数、平均时间、TPS、错误率⭐⭐⭐⭐⭐
    汇总报告全局汇总：总请求数、总失败数、吞吐量⭐⭐⭐⭐
    查看结果树调试用：每个请求的详细请求/响应⭐⭐⭐（仅调试）
    图表结果可视化：响应时间曲线、TPS 曲线⭐⭐⭐⭐
    响应时间图每个请求的响应时间分布⭐⭐⭐

    聚合报告关键指标

    指标含义关注点
    样本请求总数是否达到预期并发数
    平均时间平均响应时间 (ms)越小越好
    中位数50% 请求的响应时间比平均时间更能反映真实体验
    90% 行90% 请求的响应时间常用性能指标（P90）
    吞吐量每秒处理请求数 (TPS)核心性能指标
    错误 %失败请求占比必须接近 0%
    💡 调试技巧： 先用「查看结果树」调试单个请求，确认请求和响应都正确后，再切换到「聚合报告」看整体性能。

    9 ⌨️ 命令行运行 — CI/CD 集成

    GUI 适合调试，生产压测必须用 CLI 模式（不启动图形界面，资源消耗更小）。

    ShellCLI 基础命令
    # 基础用法：-n 非 GUI 模式
jmeter -n -t test_plan.jmx -l result.jtl

# 参数说明：
# -n  非 GUI 模式（必须）
# -t  测试计划文件
# -l  结果日志文件（.jtl）

# 生成 HTML 报告（推荐）
jmeter -n -t test_plan.jmx -l result.jtl -e -o ./report

# -e  测试结束后生成 HTML 报告
# -o  报告输出目录

    Windows 命令行

    ShellWindows CLI
    # 在 JMeter bin 目录下执行
bin\jmeter.bat -n -t test_plan.jmx -l result.jtl -e -o ./report

    常用 CLI 参数

    参数说明
    -n非 GUI 模式（必须）
    -t <file>测试计划文件
    -l <file>结果日志
    -e -o <dir>生成 HTML 报告到指定目录
    -Jthreads=100覆盖线程数（需测试计划中定义变量）
    -Jduration=300覆盖持续时间（秒）
    -Jcsv=users.csv覆盖 CSV 文件路径
    ⚠️ 压测前检查清单：
    • 移除「查看结果树」监听器（消耗大量内存）
    • 确认目标服务器能承受压测（别把生产环境压崩了）
    • 先用小并发（10 线程）跑通，再逐步加大
    • 压测时间不宜过长，一般 5-15 分钟足够

    案例 2：游戏活动接口并发压测
    Java场景：限时活动开启，大量玩家同时领取奖励
    测试计划: 活动领取压测
├── 线程组: 200 并发, 循环 10 次 (共 2000 次请求)
│   ├── CSV: test_players.csv
│   ├── HTTP 请求: POST /api/activity/claim
│   │   ├── Body: {"activity_id":"summer2026","player_id":"${player_id}"}
│   │   ├── 响应断言: 状态码 200
│   │   └── 响应断言: JSON $.code = 0
│   └── 响应时间断言: < 3000ms
└── 聚合报告
    └── 关注: 吞吐量、P90 响应时间、错误率
    💡 压测目标：
    • TPS（每秒事务数）是否达标
    • P90 响应时间是否在可接受范围（如 < 3s）
    • 错误率是否 < 1%
    • 服务器 CPU / 内存是否正常
    案例 3：阶梯式加压（找性能拐点）
    Java阶梯加压策略
    # 用吞吐量控制器实现阶梯加压
线程组:
  线程数: 10
  循环: 永远
  调度器: 开启
  持续时间: 600 秒  # 10 分钟

# 用多个线程组模拟阶梯：
线程组1: 20 并发, 持续 2 分钟
线程组2: 50 并发, 持续 2 分钟
线程组3: 100 并发, 持续 2 分钟
线程组4: 200 并发, 持续 2 分钟
线程组5: 500 并发, 持续 2 分钟

# 观察聚合报告，找到 TPS 不再增长或错误率飙升的点
# 那个点就是性能拐点
    ⚠️ 阶梯加压要点： 每阶段至少持续 1-2 分钟，让系统达到稳态。观察 TPS 是否随并发增加而增长——当 TPS 不再增长甚至下降，同时响应时间飙升，就是到了瓶颈。
