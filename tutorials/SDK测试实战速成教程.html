1 第 1 章 🧰 认识 SDK 测试

1.1 📌 SDK 是什么

SDK（Software Development Kit，软件开发工具包）是给开发者用的工具箱，而非给最终用户的产品。它把某项能力（登录、支付、推送、统计、广告等）封装成可调用的接口，让 App 快速集成。

🔑 知识点 · SDK 的组成： 一个 SDK 通常包含——库文件（.aar/.jar/.framework/.dll）、API 接口、官方文档、示例 Demo、调试工具。测试的核心就是验证这五样东西"能不能用、好不好用"。

1.2 🎯 SDK 测试与普通软件测试的区别

维度普通 App / 软件测试SDK 测试
用户是谁最终用户接入方开发者
测试视角功能好不好用集成顺不顺畅 + 调用稳不稳
可见性多为白盒/灰盒多为黑盒（只给编译好的库）
运行依赖可独立运行必须集成进宿主 App 才能跑
致命缺陷功能 bug文档错、示例跑不通、报错不清晰（开发者体验）

2 第 2 章 📋 测试准备（文档评审 + 计划）

2.1 📖 第一步：自己先集成一遍

SDK 测试的起点不是写用例，而是以接入方身份，照官方文档从零集成一遍。这一步直接验证"文档可用性"——最容易被忽略、却最影响开发者体验的测试项。

  1. 跑通 Hello World：按文档把 SDK 引入 Demo 工程，调用最简单的接口（如初始化 + 打印日志），确认能编译、能运行。
  2. 跑通官方示例：官方 Demo 能否直接编译运行？若连示例都跑不起来，这是 P0 级文档/包问题。
  3. 记录每一步的卡点：缺依赖、版本冲突、权限没写、参数名对不上——全部记录，都是缺陷。

2.2 🗂️ 拆解 API 清单

把 SDK 暴露的每个公开接口列成一张表，作为用例设计的"地图"。每个接口至少覆盖：正常调用、参数异常、边界值、依赖前置。

接口作用前置依赖关键测试点
init(config)初始化无缺 appId、重复初始化、非法 key
login()登录鉴权init 成功未初始化调用、token 过期、取消授权
pay(order)支付login 成功未登录、金额为 0、重复下单、断网
logout()登出login 成功未登录登出、登出后再调业务
⚠️【避坑：SDK 有调用顺序】
  • 多数 SDK 的接口有依赖顺序（init→login→业务→logout），乱序调用是高频缺陷来源。
  • 用例里务必设计"跳过前置直接调后续接口"的场景，验证 SDK 是否优雅报错而非崩溃。
✎ 实操练习
  1. 为你熟悉的某个 SDK 列一张 API 清单表（至少 5 个接口，含前置依赖列）。
  2. 针对 login() 接口，写出 3 个正常场景 + 3 个异常场景。

3 第 3 章 🏗️ 搭建测试环境

3.1 🧩 宿主工程（Demo App）

SDK 不能脱离 App 单独运行，必须集成进一个"测试宿主工程"。建议单独建一个干净的 Demo App，只集成被测 SDK，避免业务代码干扰定位。

3.2 📱 平台/版本矩阵

兼容性测试的前提是有一份"机型 × 系统版本"矩阵。不必全买真机，用云真机平台补齐长尾。

端需覆盖的维度建议
Android系统版本（API 21~34）、厂商 ROM（小米/华为/OPPO/vivo）、分辨率主流真机 + 云真机补长尾
iOSiOS 版本、机型（SE~Pro Max）、刘海屏适配真机为主，模拟器兜底
Unity/游戏引擎版本、打包渠道、Android/iOS 双端真机抓包，模拟器对 SDK 兼容性差

3.3 🌐 网络环境

SDK 大多依赖网络与服务端通信，网络环境是必测项：

  • 正常网：WiFi / 4G / 5G
  • 弱网：限速、高延迟、丢包（Charles 限速 / Clumsy）
  • 异常网：断网、飞行模式、网络切换（WiFi↔4G）、DNS 失败

3.4 🖥️ 服务端环境

  • 联调服/沙箱：SDK 厂商提供的测试环境（如微信沙箱、支付宝沙箱）。
  • Mock 环境：服务端没就绪时，用 Mock 服务模拟正常/异常返回，不阻塞测试。
💡 真机优先原则：涉及相机、蓝牙、推送、支付、传感器、生物识别的 SDK，模拟器/仿真器兼容性差，务必用真机测。
✎ 实操练习
  1. 新建一个空的 Demo 工程，集成一个你熟悉的 SDK，跑通初始化。
  2. 列一份你手头能用的机型/系统版本矩阵（至少 5 台设备或云真机型号）。

4 第 4 章 🛠️ 工具链全景

SDK 测试的工具按"用途"分成几类，下面这张表是核心工具链，后面章节会逐一实操。

用途工具典型场景
抓包 / 接口验证Charles、Fiddler、Whistle、Wireshark看 SDK 发了什么请求、返回什么、通信是否加密

性能 / 内存Android Profiler、PerfDog、Instruments、MAT内存泄漏、CPU/耗电、启动耗时
兼容性WeTest、优测、BrowserStack（云真机）机型/系统版本矩阵批量跑

自动化Appium、UI Automator、Airtest回归、多机型批量、冒烟
崩溃监控Bugly、CrashSight、Sentry线上崩溃聚合、堆栈还原

4.1 🔌 抓包工具：以 Charles 为例

抓包是 SDK 测试最常用的手段——验证"SDK 到底和服务端说了什么"。以 Charles 设置代理抓 HTTPS 为例：

Shell · Charles 代理
# 1. 手机与电脑连同一 WiFi，手机 WiFi 设置手动代理⟳ 手机代理指向电脑 IP+Charles 端口；动机：让 SDK 的网络请求先过 Charles 才能被抓到
代理地址 = 电脑局域网 IP（如 192.168.1.100）⟳ 填电脑 IP；动机：Charles 跑在电脑上，手机请求要能路由到它
端口 = 8888（Charles 默认）⟳ 用默认 8888；动机：与 Charles 监听端口一致，改了就抓不到
 
# 2. 手机浏览器访问 chls.pro/ssl 安装证书⟳ 装 Charles 根证书；动机：HTTPS 流量必须信任证书才能解密，否则全是乱码 <unknown>
# 3. Android 7+ 需在 res/xml/network_security_config.xml 配置⟳ 配网络安全策略；动机：高版本默认不信任用户证书，抓 HTTPS 要在清单里放行
⚠️【抓不到包排查】
  • 全是 <unknown>：证书没装或没信任 → 重装证书 + 配网络安全策略。
  • 完全没请求：代理地址/端口填错，或 SDK 用了证书绑定（SSL Pinning）→ 需让开发关闭 Pinning 或走 Hook。
  • 请求能看到但内容加密：SDK 做了二次加密 → 抓到的只是密文，需结合日志或逆向。

4.2 📜 日志采集：adb logcat

Shell · adb 日志
adb logcat -v time | grep "SDK_TAG"⟳ 按标签过滤日志；动机：SDK 日志量大，用统一 TAG 过滤才能快速定位关键行
adb logcat *:E            # 只看 Error 级⟳ 只看错误级；动机：崩溃/异常排查时先聚焦 E 级，减少噪音
adb logcat -c             # 清空缓冲⟳ 清日志缓冲；动机：复现前清空，才能拿到"本次操作"的干净日志
adb logcat -d > sdk.log   # 导出到文件⟳ 导出日志文件；动机：提 bug 时要附日志，-d 一次性 dump 便于存档
✎ 实操练习
  1. 用 Charles 抓取你 Demo App 里某 SDK 的一次网络请求，截图请求与返回。
  2. 用 adb logcat 过滤出该 SDK 的日志，找到初始化成功/失败的关键行。

5 第 5 章 ✅ 功能测试（单接口）

功能测试验证每个接口"输入→输出"是否正确。SDK 是黑盒，主要靠"传参→看返回→看副作用"来验证。方法等价类 + 边界值 + 异常输入。

5.1 🔍 等价类与边界值

以 init(appId, key) 为例，用等价类划分输入：

输入项有效等价类无效等价类（异常）边界值
appId合法非空字符串空、null、超长、含特殊字符、未注册长度 1 / 最大长度 / 超长 1 位
key合法密钥空、错误、过期—

5.2 🧪 用断言验证结果

SDK 测试也要写断言。下面用 Python + pytest 模拟对 SDK 返回结果的校验（真实项目里通过桥接调用原生 SDK，这里聚焦断言逻辑）：

Python · pytest 断言
import pytest⟳ import pytest：导入测试框架；动机：用它的断言和夹具组织 SDK 用例
 
# 模拟 SDK 初始化接口的返回结构（真实项目从桥接层拿）⟳ 注释：说明这是模拟返回；动机：SDK 是黑盒，测试先约定"期望的返回结构"
def call_init(app_id, key):⟳ def call_init：封装"调 SDK init"这一步；动机：把调用隔离成函数，用例只关心输入输出
    # 实际这里通过桥接调原生 SDK，返回 dict⟳ 注释：说明内部走桥接；动机：屏蔽平台差异，用例层拿到统一的 dict 结果
    return {"code": 0, "msg": "ok", "token": "abc"}⟳ return 模拟成功返回；动机：功能测试先验证"合法输入应得到 code=0 和 token"
 
def test_init_success():⟳ def test_init_success：正常场景；动机：验证合法输入的核心路径通过
    r = call_init("app123", "key456")⟳ 调合法参数；动机：作为基线，先保证主流程正确
    assert r["code"] == 0⟳ 断言 code=0；动机：SDK 约定 0 表示成功，非 0 即失败
    assert "token" in r and r["token"]⟳ 断言返回含非空 token；动机：登录类 SDK 必须下发凭证，空 token 是缺陷
 
def test_init_empty_appid():⟳ def test_init_empty_appid：异常场景；动机：验证空 appId 应被拒绝而非崩溃
    r = call_init("", "key456")⟳ 传空 appId；动机：构造无效等价类，看 SDK 是否优雅报错
    assert r["code"] != 0          # 应返回错误码⟳ 断言返回非 0；动机：非法输入必须被拦截，返回错误码而非 crash
💡 黑盒测试的核心心法：不关心 SDK 内部怎么实现，只验证"给定输入 → 得到期望输出 / 期望行为"。返回值、回调、异常、副作用（如是否写了本地缓存）都要纳入断言。
✎ 实操练习
  1. 为 login() 接口写 3 条 pytest 用例：正常登录、密码错误、账号为空。
  2. 思考：一个"设置用户昵称"的接口，边界值该测哪些？

6 第 6 章 🔗 链路与集成测试

SDK 的接口往往有依赖顺序，单接口通过不代表链路通过。链路测试验证"从头到尾走通一条完整业务流"。

6.1 🧭 端到端链路

以登录→支付为例，一条完整链路：

init
→
login
→
下单
→
pay
→
支付回调
→
logout

6.2 🧩 用夹具管理前置状态

链路用例要用 pytest 夹具（fixture）管理"初始化→登录"这些前置，保证每条用例都从干净状态出发：

Python · fixture 管理链路
import pytest⟳ import pytest：用它的 fixture 管前置；动机：链路测试前置多，夹具能复用且自动清理
 
@pytest.fixture⟳ @pytest.fixture：声明夹具；动机：把"初始化+登录"封装成可复用的前置
def logged_in_sdk():⟳ def logged_in_sdk：产出"已登录的 SDK 实例"；动机：用例直接拿来用，不用每条重复登录
    sdk = call_init("app123", "key456")   # 前置1：初始化⟳ 先初始化；动机：login 依赖 init 成功，顺序不能乱
    r = sdk.login("user", "pwd")      # 前置2：登录⟳ 再登录；动机：支付等业务依赖登录态，先拿到 token
    assert r["code"] == 0⟳ 断言登录成功；动机：前置失败要立即暴露，别带着坏状态跑后续
    yield sdk                          # 交给用例使用⟳ yield sdk：把实例交给用例；动机：yield 前是前置、后是清理，一个夹具管两头
    sdk.logout()                       # 后置：清理⟳ 用例后登出；动机：清理登录态，避免污染下一条用例
 
def test_pay_flow(logged_in_sdk):⟳ def test_pay_flow：支付链路用例；动机：验证"已登录→下单→支付→回调"整条走通
    order = logged_in_sdk.create_order(amount=1)⟳ 下单；动机：支付要有订单号，先创建订单拿到 order_id
    assert order["code"] == 0 and "order_id" in order⟳ 断言下单成功且返回订单号；动机：没有 order_id 就没法发起支付，是链路关键节点
    pay = logged_in_sdk.pay(order["order_id"])⟳ 发起支付；动机：用刚拿到的订单号支付，验证链路衔接正确
    assert pay["code"] == 0⟳ 断言支付成功；动机：链路终点，code=0 才算整条链路通
⚠️【链路测试避坑】
  • 数据污染：多条用例共用同一测试账号，前一条改了状态会影响后一条 → 用夹具保证每条用例前后状态干净。
  • 幂等性：支付/下单这类接口重复调用是否重复扣款？要专门测"同一订单号支付两次"。
✎ 实操练习
  1. 用 fixture 写一条"初始化→登录→查用户信息→登出"的链路用例。
  2. 设计一个"未登录直接调支付接口"的用例，验证 SDK 是否正确拒绝。

7 第 7 章 ⚡ 异常与稳定性测试

SDK 在"正常路径"下通过只是及格，异常场景下的健壮性才是拉开质量差距的关键——崩溃、ANR、内存泄漏是 SDK 最致命的缺陷。

7.1 🌪️ 异常输入与乱序调用

异常类型怎么测期望表现
参数异常传 null/空/超长/错误类型返回错误码，不崩溃
乱序调用跳过 init 直接 login明确报错，不 crash
重复调用连续 init 两次、重复支付幂等或明确拒绝，不重复扣款
并发调用多线程同时调同一接口线程安全，无数据错乱

7.2 📉 弱网与断网

Shell · Charles 弱网
# Charles 菜单 Proxy → Network Condition Settings⟳ 打开弱网设置；动机：Charles 内置限速模板，模拟 3G/弱网/丢包
# 勾选 Enable Throttling，选 "Very bad network"⟳ 选极差网络档；动机：把延迟/带宽压到极限，暴露超时处理缺陷
# 或自定义：Downlink 64kbps, Latency 500ms, 丢包 10%⟳ 自定义参数；动机：贴近真实弱网（电梯/地铁），验证超时重试是否合理
💡 弱网测试重点看：是否有超时机制（不能无限等待）、是否有重试（且重试次数有限）、超时后是否友好提示而非转圈卡死。

7.3 🧠 内存泄漏与稳定性

反复调用 SDK（如反复进出含 SDK 的页面），观察内存是否持续上涨不回落——这是内存泄漏的典型信号。用 Android Profiler 或 PerfDog 监控：

  • 反复初始化/销毁 SDK 100 次，看内存曲线是否锯齿状回落（正常）还是阶梯上涨（泄漏）。
  • 长时间挂机（Soak Test），看是否 OOM 或崩溃。
  • 结合 MAT/LeakCanary 定位泄漏对象。
✎ 实操练习
  1. 用 Charles 把网络设为"Very bad"，跑一遍登录链路，观察超时表现。
  2. 写一个循环脚本，反复初始化/销毁 SDK 50 次，用 Profiler 看内存曲线。

8 第 8 章 📱 兼容性测试

兼容性测试验证 SDK 在不同设备、系统版本、厂商 ROM、分辨率下都能正常工作。这是 SDK 分发给大量接入方时最容易出问题的环节。

8.1 🗺️ 机型矩阵策略

不必全买真机，用"核心真机 + 云真机补长尾"的组合：

层级覆盖手段
核心机型主流销量机型、各厂商旗舰本地真机，深度测
长尾机型老旧系统、小众分辨率云真机平台（WeTest/优测）批量跑
极限机型最低支持版本、最小内存专门验证下限

8.2 🔀 厂商 ROM 差异

同一 Android 版本，不同厂商 ROM 行为差异大，是兼容性重灾区：

  • 权限管理：小米/华为对后台、自启动、通知权限更严。
  • 推送：各厂商有自家推送通道（小米推送/华为 HMS），要分别测。
  • 后台保活：部分 ROM 杀后台激进，SDK 长连接易断。

8.3 🎮 游戏引擎场景（Unity）

游戏 SDK 测试的特殊性：SDK 集成在 Unity 工程里，打包成 APK/IPA 后真机测试。重点：

  • 引擎版本兼容（不同 Unity 版本 SDK 插件可能冲突）。
  • Unity 主线程 vs 子线程回调（SDK 回调线程不对会崩）。
  • 真机抓包验证（模拟器对游戏 SDK 兼容性差）。
⚠️【兼容性缺陷特征】
  • "我这台机子没问题"：兼容性 bug 的典型表现——只在特定机型/系统复现。
  • 提 bug 时必须带：机型、系统版本、ROM 版本、复现率（几台里有几台）。
✎ 实操练习
  1. 为你的 SDK 列一份兼容性矩阵（至少 8 台设备，覆盖 3 个厂商 + 3 个系统大版本）。
  2. 思考：一个推送 SDK，在小米和华为上要分别测哪些差异点？

9 第 9 章 📊 性能测试

SDK 性能直接影响宿主 App 的体验。一个"重"的 SDK（初始化慢、占内存、耗电）会被接入方投诉甚至弃用。性能测试关注几个核心指标。

9.1 📏 核心性能指标

指标含义关注点
包体积SDK 引入后 APK/IPA 增大多少是否可接受，能否按需引入
初始化耗时init 调用到可用的时间是否阻塞主线程、能否异步
内存占用运行时常驻内存是否泄漏、常驻是否过高
CPU / 耗电运行时资源消耗后台是否偷跑、长连接是否耗电
启动耗时对 App 冷启动的拖累SDK 初始化是否拖慢首屏

9.2 ⏱️ 初始化耗时测量

Python · 计时
import time⟳ import time：用它的计时函数；动机：测 init 耗时只需记录前后时间差
 
def measure_init(sdk_factory, rounds=5):⟳ def measure_init：测初始化耗时；动机：单次有波动，跑多轮取平均更可靠
    total = 0.0⟳ 累计耗时；动机：多轮求和后再平均，抹平单次抖动
    for i in range(rounds):⟳ 跑 5 轮；动机：样本太少不具代表性，5 轮是成本与可信的折中
        t0 = time.time()⟳ 记录起始时间；动机：在 init 前打点，才能算出纯初始化耗时
        sdk_factory()⟳ 执行初始化；动机：把被测动作夹在两个时间点中间
        total += time.time() - t0⟳ 累加本轮耗时；动机：把每轮差值累加，最后除以轮数得平均
    return total / rounds * 1000  # 转毫秒⟳ 返回平均毫秒数；动机：乘 1000 换算成 ms，符合"初始化耗时"的常用单位

9.3 🔋 耗电与后台行为

涉及定位、长连接、定时上报的 SDK，要重点测耗电：用 PerfDog 或系统电量统计，观察后台运行时是否异常耗电（如定位频率过高、心跳太频繁）。

💡 性能测试要有基线对比：测"接入 SDK 前"与"接入后"的启动耗时、内存、包体积差值，才能量化 SDK 的开销，而非看绝对值。
✎ 实操练习
  1. 测量你的 SDK 初始化平均耗时（跑 5 轮取平均）。
  2. 对比"接入 SDK 前后"的 App 冷启动耗时差值。

10 第 10 章 🐞 缺陷定位与提单

SDK 是黑盒，出了 bug 定位难、提单更难。测试人员的价值在于把"复现不了"的 bug 变成"开发能看懂、能复现"的缺陷单。

10.1 🔎 定位三板斧

  1. 抓包：看 SDK 发出去的请求对不对、服务端返回对不对——区分"SDK 逻辑错"还是"服务端错"。
  2. 看日志：adb logcat / Xcode Console 抓 SDK 内部日志和崩溃堆栈。
  3. 缩小范围：二分法——注释掉一半调用，定位是哪一步、哪个参数触发。

10.2 📝 高质量缺陷单要素

SDK 缺陷单必须让厂商开发能复现，要素缺一不可：

要素说明
环境信息机型、系统版本、ROM、SDK 版本、App 版本
复现步骤1.2.3. 精确到每一步操作
实际结果发生了什么（附崩溃堆栈/抓包截图/日志）
期望结果应该是什么
复现率必现 / 偶现（几台里有几台、几次里有几次）
附件logcat 日志、抓包文件、崩溃堆栈、录屏
⚠️【提单红线】
  • 不要只写"崩溃了"：没有堆栈和复现步骤的 bug 单，开发无法定位，等于没提。
  • 区分责任方：抓包后能判断是 SDK 端错还是服务端错，帮开发少走弯路。
  • 偶现 bug 也要提：记录复现率，附长时间挂机日志，别因"我这边没复现"就忽略。
✎ 实操练习
  1. 假设你发现某 SDK 在弱网下登录偶发崩溃，写一份完整缺陷单（含 6 要素）。
  2. 练习用二分法：一段链路崩了，如何快速定位是哪一步的问题？

11 第 11 章 📇 知识点速查

知识点一句话速记
SDK 定义给开发者用的工具包（库+API+文档+示例+工具），非终端产品
测试视角站接入方开发者视角，验证"能集成、能调用、够稳定、文档准"
六大维度功能 / 集成 / 兼容性 / 稳定性 / 性能 / 安全文档
黑盒特性多为黑盒，只测输入→输出与集成行为
调用顺序接口有依赖（init→login→业务），乱序是高频缺陷
抓包工具Charles/Fiddler/Whistle；HTTPS 要装证书
日志工具adb logcat（Android）/ Xcode Console（iOS）
性能工具Android Profiler / PerfDog / Instruments / MAT
兼容性核心真机 + 云真机补长尾；厂商 ROM 差异大
弱网Charles 限速；看超时/重试/友好提示
内存泄漏反复调看内存曲线，阶梯上涨=泄漏
幂等性重复调用不重复扣款/不重复创建
真机优先相机/蓝牙/推送/支付/传感器必须真机
缺陷单环境+步骤+实际+期望+复现率+附件，缺一不可
性能基线对比接入前后差值，量化 SDK 开销
