1 第 1 章 🤖 认识接口自动化测试

1.1 📌 一句话认识

接口自动化测试，就是用代码代替人工，自动向后端接口发请求、拿响应、核对结果。它不关心页面长什么样，只关心「输入 → 输出」是否正确，是测试金字塔里投入产出比最高的一层。

💡 一句话总结： 接口自动化 = 用脚本模拟客户端请求 + 自动断言响应，把「点接口、看返回」这件重复劳动交给程序。

1.2 🎯 为什么优先做接口自动化

对比维度UI 自动化接口自动化
稳定性易受页面改版影响接口契约相对稳定
执行速度慢（要渲染、等待）快（毫秒级返回）
维护成本高低
覆盖后端逻辑间接直接命中业务逻辑
CI 集成较重轻量，秒级反馈

3.3 📬 状态码速记

状态码含义测试时怎么看
200成功正常，继续断言响应体
201创建成功常见于 POST 新建资源
400参数错误参数校验类用例的期望值
401未认证token 缺失/失效场景
403无权限越权测试期望值
404资源不存在查不存在的 id 期望值
500服务器内部错误非期望，出现即缺陷

11.4 🔑 核心概念一句话速记

  • 接口关联： 上一个接口的返回值（token/id）存变量，传给下一个接口。
  • Session： 自动管 cookie 的会话对象，登录态用它。
  • fixture： pytest 的依赖注入，抽公共准备逻辑，用例按参数名取用。
  • parametrize： 变量名+数据列表，一份逻辑跑多组数据。
  • 断言三层： 状态码 → 业务码 → 关键字段值。
  • 数据分离： 数据放 YAML/JSON，代码只读不写死。
  • 分层目录： common 封装 / data 数据 / testcases 用例。

1什么是接口自动化测试？它和 UI 自动化有什么区别？基础
回答要点
定义 + 测试金字塔位置 + 与 UI 的稳定性/速度/维护成本对比。
参考答案
接口自动化是用代码模拟客户端请求并自动断言响应，位于测试金字塔中层。相比 UI 自动化：更稳定（不依赖页面渲染）、更快（毫秒级）、维护成本更低、能直接覆盖后端业务逻辑。UI 自动化测交互体验，接口自动化测逻辑正确性，二者互补。
回答红线
不能说「接口自动化能完全替代 UI 自动化」——二者覆盖层面不同，是互补关系。
2HTTP 常见的请求方法有哪些？GET 和 POST 的区别？基础
回答要点
列出方法 + GET/POST 在参数位置、长度限制、幂等性、安全性上的差异。
参考答案
常见方法：GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS。GET 参数在 URL 上、有长度限制、幂等、可被缓存；POST 参数在请求体、无长度限制、非幂等、相对更安全。PUT 全量更新、PATCH 部分更新、DELETE 删除。
回答红线
不要说「POST 比 GET 安全所以敏感数据一定用 POST」——POST 数据仍明文可见，真正安全要靠 HTTPS 加密传输。
3状态码 200、401、403、404、500 分别代表什么？基础
回答要点

参考答案
200 成功；401 未认证（token 缺失/失效）；403 已认证但无权限（越权）；404 资源不存在；500 服务器内部错误。测试中 4xx 常是参数/权限类用例的期望值，500 通常是非预期缺陷。
回答红线
不要混淆 401 和 403：401 是「没登录/身份不明」，403 是「登录了但没权限」。

参考答案
json= 会把 dict 序列化为 JSON 并设置 Content-Type: application/json；data= 发送 application/x-www-form-urlencoded 表单。现代接口多用 JSON，传错会导致服务端解析不到参数。
回答红线
不能说「两者没区别，随便用」——Content-Type 不同，服务端解析逻辑不同，用错直接 400。

回答要点

参考答案
默认 requests 无超时，网络异常时会一直等待，导致脚本挂死、CI 流水线卡住。加 timeout 可设定连接/读取超时上限，异常时快速失败。可写 timeout=(连接超时, 读取超时)。
回答红线
不要认为「本地能跑就不用加」——本地网络好不代表测试环境/CI 稳定。

不要说「每个接口独立调用即可」——有依赖的接口不关联会 401/查不到数据。

Session 是会话对象，能在多次请求间自动保存 cookie、复用 headers/base_url 等公共配置，并底层复用 TCP 连接提升性能。适合需要维持登录态的连续请求场景。

不要每次请求都 new 一个 Session 又指望保持登录态——要复用同一个实例。

参考答案
① HTTP 状态码；② 业务码 code（很多接口业务失败也返回 200）；③ 关键响应字段的值。只断状态码不够，必须断业务码和核心数据字段。

12为什么很多接口业务失败也返回 200？你怎么处理？进阶

部分后端未严格遵循 RESTful，HTTP 层统一 200，用 body 里的 code/msg 表达业务成败。处理：断言时必须检查业务码 code 字段，不能只看 HTTP 状态码，否则缺陷会漏网。

不能说「返回 200 就是成功」——这是新手最常踩的坑。

conftest.py 是 pytest 的特殊文件，里面定义的 fixture 无需 import，同目录及子目录下的用例可直接按参数名使用。常用来放全局登录 token、session 等共享资源，可分层放置实现就近覆盖。

回答要点

参考答案
scope 控制 fixture 生命周期：function（默认，每条用例执行）、class（每个测试类一次）、module（每个文件一次）、session（整个测试会话一次）。登录拿 token 这类昂贵操作应用 session 级避免重复请求。

RESTful 是用 HTTP 方法语义操作资源的风格：URL 表示资源，GET 查、POST 增、PUT 改、DELETE 删，状态码语义化。对测试：可用状态码判断操作结果，但现实中很多接口不规范，仍需断言业务码。
回答红线
不要假设被测接口一定严格 RESTful——实际项目常不严格，要按实际返回断言。
33如何用 pytest 只运行失败的用例或指定优先级用例？框架
回答要点
-m 按 marker + --lf 只跑上次失败 + -k 关键字。
参考答案
按优先级用 marker：pytest -m P0；只跑上次失败用 pytest --lf（需配合 --cache-dir）；按名字用 pytest -k 关键字。合理组合能精准控制执行范围。
回答红线
不要每次全量跑——善用 -m/--lf/-k 提升反馈速度。
34测试环境和生产环境的接口测试要注意什么？工程
回答要点
环境隔离 + base_url 切换 + 生产谨慎 + 数据脱敏。
参考答案
用配置区分环境（base_url 从配置读，不写死），测试环境可随意造数据。生产环境要极其谨慎：避免写操作污染真实数据、注意限流、数据脱敏、最好只读或走专门的测试账号。
回答红线
不要拿测试脚本直接怼生产环境跑写操作——可能污染真实业务数据。
35你如何保持接口自动化用例的长期可维护性？综合
回答要点
分层 + 数据分离 + 封装 + 命名规范 + 定期清理。
参考答案
① 分层解耦，接口变更只改封装；② 数据外置，改数据不动代码；③ 公共逻辑抽 fixture/工具；④ 用例命名清晰、一个用例验证一个点；⑤ 定期清理失效用例、修复 flaky；⑥ 加断言信息让失败自解释。
回答红线
不要为了赶进度堆砌重复代码——技术债会让后期维护成本指数上升。
36接口自动化能 100% 覆盖所有场景吗？为什么？综合
回答要点
不能 + 成本/收益 + 结合手工与其他层。
参考答案
不能。自动化适合回归核心逻辑和高频场景，但边界组合爆炸、UI 交互、体验类、探索性场景自动化成本高、收益低。应遵循测试金字塔，自动化覆盖稳定核心，手工测试聚焦复杂/易变场景，二者结合。
回答红线
不要吹嘘「自动化能覆盖全部」——不切实际，面试官会认为你缺乏工程判断。
