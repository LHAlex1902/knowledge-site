2第 1 章 抓包基础与原理

1.1 什么是抓包

抓包（Packet Capture）是指截获并查看设备与服务器之间网络通信数据的过程。对测试而言，抓包是定位「接口报错、数据不对、请求没发出、响应慢」等问题的第一手段。

1.2 HTTP 与 HTTPS

HTTP 是明文传输，抓包工具可直接看到请求与响应内容。但现代 App 几乎全部使用 HTTPS（HTTP + TLS 加密），数据加密后抓包工具默认只能看到密文，需要额外安装证书才能解密。

对比项HTTPHTTPS
传输明文TLS 加密
默认端口80443
抓包可见性直接可读需装证书解密
测试重点几乎不用证书是核心难点

1.3 代理（Proxy）原理

抓包工具本质是一个「中间人代理」（Man-in-the-Middle, MITM）。设备把本该发给服务器的请求先发给抓包工具，工具解密、展示后再转发给真实服务器，响应原路返回。

流程：

  1. 手机设置代理指向抓包工具监听的 IP + 端口（如 192.168.1.100:8888）
  2. 手机请求先到达抓包工具
  3. 工具解密请求 → 展示 → 转发给真实服务器
  4. 服务器响应 → 工具 → 手机
【关键】手机和抓包电脑必须在同一局域网（同一 WiFi），或电脑开启热点让手机连接。

1.4 证书与 HTTPS 解密

HTTPS 抓包的核心是「让手机信任抓包工具的根证书」。工具用它自签的根证书对请求做 TLS 握手，从而解密内容。因此抓 HTTPS 包的两步是：

  • 第一步：配置代理，让流量经过工具
  • 第二步：安装并信任工具的根证书（iOS 还需在「关于本机 → 证书信任设置」中手动开启信任）
【警告】证书安装环节是新手最容易卡住的地方，也是第 3、4 章的重点。Android 7.0 以上系统证书默认不被 App 信任，需要额外处理（见 3.3）。

2.2 Charles 快速上手

步骤：

  1. 打开 Charles，菜单 Proxy → Proxy Settings，确认 HTTP Proxy 端口（默认 8888），勾选 Enable transparent HTTP proxying
  2. 菜单 Help → SSL Proxying → Install Charles Root Certificate，按提示安装证书到系统钥匙串/信任库
  3. 手机与电脑连同一 WiFi，手机 WiFi 设置里配置手动代理：服务器=电脑IP，端口=8888
  4. 手机浏览器访问 chls.pro/ssl 下载并安装证书
  5. 在 Charles 左侧 Structure/Sequence 面板即可看到请求列表，点击查看详情
【技巧】Charles 里右键某个请求可 Save Response / Repeat / Edit and Repeat，用于复现和改包测试。

2.3 Fiddler 快速上手

  1. Tools → Options → HTTPS，勾选 Decrypt HTTPS traffic，按提示安装根证书
  2. Connections 页确认 Fiddler listens on port 8888，勾选 Allow remote computers to connect
  3. 手机配置代理指向电脑 IP:8888，安装证书（浏览器访问 192.168.x.x:8888/FiddlerRootCert）
  4. 在左侧会话列表查看请求，右侧 Inspector 查看明细

2.4 mitmproxy 快速上手（推荐自动化）

mitmproxy 是命令行工具，三兄弟：mitmproxy（交互 TUI）、mitmdump（纯 dump，适合脚本）、mitmweb（Web 界面）。

代码
pip install mitmproxy

# 启动 Web 界面，端口 8080，手机代理指向电脑:8080
mitmweb --listen-port 8080

# 命令行查看
mitmdump

# 首次启动会自动生成证书，位于 ~/.mitmproxy/
【证书路径】mitmproxy 证书在 ~/.mitmproxy/mitmproxy-ca-cert.pem，手机需安装此证书才能解 HTTPS。

4第 3 章 Android 抓包实战

3.1 环境准备

  • 电脑安装好抓包工具（以 Charles 为例）
  • Android 手机或模拟器（MuMu、夜神、Android Studio AVD 均可）
  • 手机与电脑在同一 WiFi，或电脑开热点

3.2 配置代理并抓 HTTP 包

  1. 手机 WiFi → 长按已连接网络 → 修改 → 手动代理 → 填电脑 IP 和端口 8888
  2. 打开 App，操作目标功能
  3. Charles 中即可看到请求。HTTP 请求无需证书即可看到内容

3.3 攻克 HTTPS 抓包

难点：Android 7.0（API 24）起，App 默认不信任用户安装的证书，只信任系统级证书。因此 HTTPS 抓包有两种方案：

方案适用做法
方案A：装系统证书已 root 的设备/模拟器把证书转成系统证书格式放入 /system/etc/security/cacerts/
方案B：改 App 让它信任用户证书可改包/测试包修改 network_security_config.xml 或使用 debug 包
方案C：用低版本系统快速验证用 Android 6.x 模拟器抓包

3.3.1 模拟器 + 系统证书方案（推荐）

Shell / ADB
# 1. 用 MuMu/夜神模拟器（自带 root），浏览器访问工具证书地址下载安装
# 2. 找到证书文件，转成系统证书格式（需 root）
# 模拟器里用 MT 管理器/NP Manager 将证书移动到系统证书目录
# 证书命名规则：<hash>.0，hash 为证书 subject 的 md5

# 3. 用 adb 辅助操作（见第 5 章）
adb shell
su                          # 获取 root
cp /sdcard/Download/charles.crt /system/etc/security/cacerts/charles.crt
chmod 644 /system/etc/security/cacerts/charles.crt
reboot

3.4 Android 抓包常见坑

现象原因解决
只能看到 CONNECT，看不到内容HTTPS 且证书未信任按 3.3 装系统证书
App 打不开/报网络错误证书校验失败或 App 有 SSL Pinning用低版本系统/改包/绕过 Pinning
完全抓不到包代理没生效或不在同网段检查代理 IP、端口、防火墙
部分请求抓不到App 用了证书绑定(SSL Pinning)需 Frida/JustTrustMe 等绕过
【SSL Pinning】很多金融、大厂 App 做了证书绑定，普通代理抓不到。测试环境一般可用测试包/开关关闭，生产环境需借助 Frida、Xposed 模块绕过（仅限授权测试）。

5第 4 章 iOS 抓包实战

4.1 iOS 抓包特点

iOS 抓包强烈建议使用真机（模拟器网络走宿主机，抓包不便）。iOS 证书安装比 Android 多一步「手动信任」，这是新手最常漏掉的环节。

4.2 真机抓包步骤（Charles 为例）

  1. iPhone 与电脑连同一 WiFi（或电脑开热点给手机连）
  2. Charles 开启代理 8888 端口，安装 Charles 根证书到 Mac/Windows 系统
  3. iPhone：设置 → 无线局域网 → 当前 WiFi 右侧 ⓘ → 配置代理 → 手动 → 填电脑 IP 和 8888
  4. iPhone Safari 访问 chls.pro/ssl 下载描述文件并安装（设置里需输入锁屏密码确认）
  5. 关键：设置 → 通用 → 关于本机 → 证书信任设置 → 打开 Charles 证书的「完全信任」开关
  6. 打开 App 操作，Charles 即可看到 HTTPS 请求明文
【最容易漏的一步】第 5 步「证书信任设置」开关。只安装不信任，HTTPS 依然抓不到，只会显示 unknown 或握手失败。

4.3 iOS 抓包工具链补充

工具说明
Charles / Fiddler图形界面，日常抓包
mitmproxy命令行，配合 iPhone 代理抓包，可脚本化
rvictl / Wireshark抓取真机底层数据包（需 iTunes 备份），进阶用
ProxymanMac 上体验优秀的抓包工具，对 iOS 支持好

4.4 iOS 抓包常见坑

现象原因解决
证书装了仍抓不到 HTTPS未开启「完全信任」去证书信任设置打开开关
描述文件装不上iOS 版本高/Safari 拦截用 Safari 访问，注意大小写 chls.pro/ssl
App 有 SSL Pinning证书绑定越狱 + SSL Kill Switch / Frida（授权测试）
抓一会就断代理不稳定/热点休眠关闭电脑休眠，保持稳定网络

sed -i &#x27;s/foo/bar/g&#x27; file.txt       # 直接改文件

# awk：按列处理
awk &#x27;{print $1, $3}&#x27; data.txt       # 打印第1、3列

7第 6 章 日志抓取

6.1 Android 日志：adb logcat

adb 是 Android 调试桥，logcat 是抓取设备日志的核心命令。前提：手机开启「开发者选项 + USB 调试」，电脑 adb devices 能识别设备。

6.1.1 常用 adb 命令

命令作用
adb devices查看连接的设备
adb shell进入设备 shell
adb install app.apk安装 App
adb pull /sdcard/file ./从设备拉取文件
adb push file /sdcard/推送文件到设备
adb reboot重启设备
adb logcat查看日志

6.1.2 logcat 实战

Shell / ADB
# 查看全部日志
adb logcat

# 按 Tag 过滤（App 自定义的日志标签）
adb logcat -s MyTag

# 按级别过滤（V/D/I/W/E/F，只看 Error 及以上）
adb logcat *:E

# 过滤关键字（配合 grep）
adb logcat | grep &#x27;MyApp&#x27;
adb logcat | grep -iE &#x27;error|exception|crash&#x27;

# 导出到文件
adb logcat &gt; app_log.txt
adb logcat -d &gt; app_log_full.txt   # -d 抓完即退出

# 清空缓冲 + 只抓指定进程
adb logcat -c
adb shell pidof com.example.app    # 拿包名对应 pid
adb logcat --pid=&lt;pid&gt;
【技巧】复现问题时：先 adb logcat -c 清缓冲 → 操作 App 触发问题 → adb logcat -d > bug.log 一次性导出，日志干净不掺别的操作。

6.1.3 崩溃日志定位

App 崩溃时，logcat 里通常有 FATAL EXCEPTION 或 AndroidRuntime 关键字：

Shell / ADB
adb logcat *:E | grep -A20 &#x27;FATAL EXCEPTION&#x27;
adb logcat | grep -iE &#x27;AndroidRuntime|CRASH|SIGSEGV&#x27;

崩溃堆栈一般包含：异常类型、出错类/方法、行号，把它交给开发或贴到 Bug 单即可。

8第 7 章 日志分析方法与实战

7.1 日志分析的基本思路

  1. 确定时间窗口：问题发生在几点几分，缩小范围
  2. 定位关键字：ERROR / Exception / crash / timeout / 状态码
  3. 还原调用链：用 TraceId / 请求 ID 把一条请求的完整链路串起来
  4. 关联上下文：崩溃前的最后几条日志往往就是线索
  5. 复现与验证：清缓冲 → 复现 → 对比日志

7.2 高频关键字清单

类别关键字
崩溃FATAL EXCEPTION, AndroidRuntime, SIGSEGV, signal 11, crash
异常Exception, Error, Throwable, NullPointerException, TimeoutException
网络timeout, connection refused, 4xx, 5xx, SSLException, UnknownHost
ANRANR in, Input dispatching timed out, Broadcast of Intent
内存OutOfMemoryError, GC, lowmemorykiller, OOM
业务自定义错误码，如 code=500, ret=-1, msg=fail

7.3 实战：定位一次崩溃

场景：App 点击「提交订单」后闪退。

Shell / ADB
# 步骤 1：清缓冲
adb logcat -c

# 步骤 2：复现并抓日志
adb logcat &gt; order_crash.log
# （在 App 里点击提交订单，触发闪退）

# 步骤 3：过滤崩溃
grep -A30 &#x27;FATAL EXCEPTION&#x27; order_crash.log

# 步骤 4：看崩溃前最后几条（提交订单相关）
grep -B10 &#x27;FATAL EXCEPTION&#x27; order_crash.log | grep -i &#x27;order\|submit&#x27;

分析要点：

  • 看异常类型：NullPointerException 多为空值未判
  • 看堆栈第一处业务代码行号 → 定位到具体类和方法
  • 结合抓包：若接口返回 500，则是后端问题；若接口正常但解析崩溃，则是客户端解析问题

7.4 抓包 + 日志联合分析

真正高效的定位是「抓包看接口 + 日志看客户端」双管齐下：

现象抓包结论日志结论
页面空白接口没发出 → 客户端逻辑问题有请求构造异常日志
页面空白接口 404/500 → 后端问题客户端日志正常
数据错乱接口返回数据就错 → 后端解析日志与返回一致
数据错乱接口正常，解析字段错位 → 客户端解析逻辑日志异常
很慢接口响应耗时长 → 后端/网络等待接口耗时日志

9第 8 章 Python 自动化脚本

本章用 Python 把抓包与日志分析自动化。遵循 PEP 8，使用现代 Python 3.10+ 语法。

8.1 用 mitmproxy 脚本自动记录请求

mitmdump 可加载 Python 脚本，实时处理每个请求/响应。写一个 addon：

Python
# save_requests.py —— 记录所有请求到 requests.log
import json
from datetime import datetime
from mitmproxy import http

def response(flow: http.HTTPFlow) -&gt; None:
    record = {
        &#x27;time&#x27;: datetime.now().isoformat(),
        &#x27;method&#x27;: flow.request.method,
        &#x27;url&#x27;: flow.request.pretty_url,
        &#x27;status&#x27;: flow.response.status_code,
        &#x27;cost_ms&#x27;: flow.response.timestamp - flow.request.timestamp,
    }
    with open(&#x27;requests.log&#x27;, &#x27;a&#x27;, encoding=&#x27;utf-8&#x27;) as f:

8.2 自动分析日志文件

写一个脚本统计日志中的错误分布，输出 Top 报错：

Python
# analyze_log.py —— 统计日志错误 Top N
import re
from collections import Counter
from pathlib import Path

LOG_FILE = &#x27;app_log.txt&#x27;
ERROR_PATTERN = re.compile(r&#x27;(ERROR|Exception|CRASH)&#x27;, re.I)

def analyze(top_n: int = 10) -&gt; None:
    path = Path(LOG_FILE)
    if not path.exists():
        raise FileNotFoundError(f&#x27;日志文件不存在: {LOG_FILE}&#x27;)
    counter: Counter[str] = Counter()
    for line in path.read_text(encoding=&#x27;utf-8&#x27;, errors=&#x27;ignore&#x27;).splitlines():
        if ERROR_PATTERN.search(line):
            counter[line.strip()[:120]] += 1
    print(f&#x27;共发现 {sum(counter.values())} 条错误，去重后 {len(counter)} 类：&#x27;)
    for msg, cnt in counter.most_common(top_n):
        print(f&#x27;[{cnt:&gt;4}] {msg}&#x27;)

if __name__ == &#x27;__main__&#x27;:
    analyze()

# 运行：python analyze_log.py

8.3 用 subprocess 自动抓 adb 日志

把「清缓冲 → 抓一段时间 → 过滤 → 存文件」封装成脚本：

Shell / ADB
# capture_adb.py —— 自动抓取并过滤 adb 日志
import subprocess
import time
from datetime import datetime

DURATION_SEC = 30
KEYWORDS = [&#x27;ERROR&#x27;, &#x27;Exception&#x27;, &#x27;crash&#x27;]

def capture() -&gt; str:
    subprocess.run([&#x27;adb&#x27;, &#x27;logcat&#x27;, &#x27;-c&#x27;], check=True)
    print(f&#x27;开始抓取 {DURATION_SEC} 秒...&#x27;)
    proc = subprocess.Popen(
        [&#x27;adb&#x27;, &#x27;logcat&#x27;], stdout=subprocess.PIPE,
        text=True, encoding=&#x27;utf-8&#x27;, errors=&#x27;ignore&#x27;)
    lines: list[str] = []
    start = time.time()
    for line in proc.stdout:
        if time.time() - start &gt; DURATION_SEC:
            break
        if any(k in line for k in KEYWORDS):
            lines.append(line)
    proc.terminate()
    out = f&#x27;adb_{datetime.now():%Y%m%d_%H%M%S}.log&#x27;
    open(out, &#x27;w&#x27;, encoding=&#x27;utf-8&#x27;).writelines(lines)
    print(f&#x27;已保存 {len(lines)} 条到 {out}&#x27;)
    return out

if __name__ == &#x27;__main__&#x27;:
    capture()

9.4 高频问题排查决策树

接口请求失败：

  • 抓不到包 → 代理没生效 → 检查代理 IP/端口/同网段/防火墙
  • 能抓到但显示密文/CONNECT → HTTPS 未解密 → 检查证书安装与信任
  • 抓到包但 App 报网络错误 → 可能 SSL Pinning → 授权测试下绕过

App 崩溃：

  • logcat 有 FATAL EXCEPTION → 看异常类型 + 首个业务堆栈行号 → 提单给开发
  • 无 Exception 但进程被杀 → 看是否 OOM / lowmemorykiller → 内存问题
  • ANR → 主线程阻塞 → 抓 traces 文件分析
