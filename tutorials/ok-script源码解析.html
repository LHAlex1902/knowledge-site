1 第 1 章 🧭 框架总览：它到底做了什么

ok-script 是一个基于图像识别的游戏自动化框架。它的全部工作，本质就是一个不断重复的循环——截一张图 → 在图里找目标 → 决定点哪 → 模拟点击 → 等界面变化 → 再截一张图。看懂这个循环，就看懂了整个框架。

💡 本文档怎么读： 所有代码都来自 ok-script 真实源码（ok/ 目录）。每一行代码右侧都有一列注释，解释「这行在做什么、为什么这么写」。

1.1 🎯 框架解决的核心难题

难题ok-script 的解法对应源码模块
游戏画面是引擎渲染的，抓不到控件改用图像识别：截图后在像素里找模板ok/feature/
想让游戏后台跑（最小化/被遮挡）用 Win32 BitBlt 直接抓窗口画面，不依赖屏幕ok/device/capture_methods/bitblt.py
后台时鼠标不能真动（用户在用电脑）用 PostMessage 直接向窗口句柄发键鼠消息ok/device/interaction_methods/post_message.py

✎ 一句话抓住本质： ok-script = Win32 后台截图 + OpenCV 模板匹配 + Win32 后台键鼠 + 一层好用的任务 API。本文档就按这四块，一块块拆给你看。

2 第 2 章 🏗️ 架构分层：代码是怎么组织的

ok-script 的 ok/ 包按职责分成清晰的几层。越靠下越是「操作系统的脏活」，越靠上越是「用户写的业务」。这种分层让业务代码可以很干净。

层目录职责（逐行注释）
任务层ok/task/用户写业务的地方：BaseTask 基类、任务执行器 TaskExecutor
特征层ok/feature/图像识别核心：Feature 模板、Box 坐标框、FeatureSet 匹配算法
设备层ok/device/截图与输入的具体实现，分 Windows / ADB 两大类
核心层ok/core/事件系统、任务管理、截图通信、翻译等通用能力
UI 层ok/ui/Qt 桌面界面 / Web 界面（可选，与核心解耦）
工具层ok/util/配置、日志、颜色、窗口操作等零碎工具
💡 依赖方向（重要）： 上层依赖下层，下层不知道上层存在。任务层调用特征层做识别，特征层调用设备层做截图——但设备层绝不会反过来调用任务层。这样换掉 UI（比如从 Qt 换成 Web）完全不影响核心逻辑。

2.1 🔌 设备层的双轨设计（Windows / ADB）

设备层最值得学的是它的「面向接口编程」：capture_methods/ 和 interaction_methods/ 各有基类，Windows 和 ADB（安卓）各自实现一套。业务代码只调基类方法，运行时用哪套由配置决定。

# bitblt.py    —— Windows BitBlt 后台截图（★核心，本文第4章详解）
# hwnd_window.py —— 封装 Windows 窗口句柄信息（坐标、尺寸）

✎ 设计模式提炼： 这就是策略模式（Strategy Pattern）。基类定接口，子类定实现，运行时可替换——你以后写任何自动化框架都能套用这个思路。

3 第 3 章 🖼️ Feature：一张「模板图」在代码里长什么样

我们从最简单的类开始。Feature 代表一张从游戏里截下来的小图（模板），比如一个「确认按钮」的截图。它是整个识别系统的最小数据单元。

Pythonok/feature/Feature.py（完整源码 + 逐行注释）
import numpy as np# 导入 numpy 并简写为 np；图像在 Python 里就是 ndarray 数组，后面的像素运算全靠它
 
class Feature:# 定义 Feature 类；它把「一张模板图 + 图的左上角坐标」捆成一个对象，作为识别系统的最小数据单元
    # __init__：创建一个 Feature 要给它一张图，以及这张图在屏幕上的位置
    def __init__(self, mat: np.ndarray, x: int = 0, y: int = 0, scaling=1) -> None:# 构造方法：收下模板图和它的屏幕位置；x/y/scaling 给默认值，只关心图、不关心位置时也能直接构造
        self.mat = mat# 存下模板图像数组；原样保存不做转换，因为后面 OpenCV 匹配要的就是这个 BGR 格式的原始数组
        self.scaling = scaling# 存下缩放系数；不同分辨率的屏幕要用不同尺寸的模板，记下比例才能把匹配结果换回真实坐标
        self.x = round(x)# 记下左上角 x；统一 round 成整数像素，避免浮点坐标传到 numpy 切片里被静默取整而出错
        self.y = round(y)# 记下左上角 y；和 x 一起构成这个模板在屏幕上的定位基准，后续所有换算都从它出发
        self.mask = None# 掩码先置空；匹配时可以靠它忽略透明区或干扰像素，平时用不上就先占位，需要时再赋值
        self.template_cache = {}# 建一个空字典当模板缓存；灰度化、Canny 边缘这些预处理很耗时，缓起来避免每帧都重算一遍
 
    @property# 用 @property 把方法伪装成属性；外部写 feature.width 而不是 feature.width()，读起来更自然
    def width(self):# 定义 width 属性；宽度不单独存字段而是实时算出来，图像一变宽度自动跟着变，不会出现两份数据对不上
        return self.mat.shape[1]# 取 shape[1] 当宽度；OpenCV 的 shape 顺序是 (高, 宽, 通道)，下标写 1 才是宽 —— 这里最容易写反
 
    @property# 同样用 @property 暴露 height；和 width 保持一致的访问手感，业务不用记哪个是方法哪个是属性
    def height(self):# 定义 height 属性；同样实时计算，不额外占内存，也避免忘了同步更新
        return self.mat.shape[0]# 取 shape[0] 当高度；第 0 维是行数也就是高，和 width 正好差一个下标，成对记忆就不易错
 
    def __str__(self) -> str:# 定义 __str__；这样 print(feature) 就能直接看到坐标和尺寸，调试不用再手动拼字符串
        return str(f'self.x: {self.x}, self.y: {self.y}, width: {self.width}, height: {self.height}')# 拼成一行可读信息；排查「匹配位置偏了」这类问题时，一眼就能看到模板本该在哪、有多大
💡 关键认知： 一张图 = 一个 numpy 数组 + 一个左上角坐标。就这么简单。后面所有的「找图」，本质都是「在大图数组里找一小块和它最像的区域」。mask 和 template_cache 是为匹配精度与性能做的优化。
⚠️【易错点】shape 的行列： OpenCV 图像的 shape 是 (高, 宽, 通道)，即 (行, 列, 通道)。所以 height 取 shape[0]（行），width 取 shape[1]（列）——新手极易写反。

4 第 4 章 📐 Box：识别结果的「坐标+置信度」载体

Box 代表屏幕上的一块矩形区域。它有两个用途：① 当「搜索范围」——只在某块区域里找图，提速；② 当「匹配结果」——找到目标后，用 Box 把坐标和置信度返回给业务。

Pythonok/feature/Box.py（核心方法 + 注释）
class Box:# 定义 Box 类；一块矩形区域承担两个角色 —— 当搜索范围可缩小匹配面积，当匹配结果可承载坐标和置信度
    # 构造一个矩形框：左上角(x,y) + 宽高 + 匹配置信度 + 名字
    def __init__(self, x, y, width, height, confidence=1.0, name=None):# 后两个参数给了默认值；只传坐标也能构造出一个 Box，名字和置信度等业务需要时再补，降低调用负担
        self.x = x# 记下左上角 x；中心点计算和裁剪都以它为基准，必须先存下来
        self.y = y# 记下左上角 y；和 x 一起构成矩形的定位原点，少任何一个坐标都算不出中心点和裁剪范围
        self.width = width# 记下宽度；算中心、算相对坐标、裁剪子图都要用，单独存一份免得每次重算
        self.height = height# 记下高度；用途同上，宽高成对保存，后续公式才读得清楚
        self.confidence = confidence# 记下置信度（0~1）；业务可以拿它做二次筛选，比如「只要 0.98 以上才算数」就靠这个字段
        self.name = name# 记下名字；匹配结果带着名字返回，日志里能直接看出点到的是哪个按钮，不用回去数下标
 
    @property# 用 @property 暴露 center；中心点最常用，但它由坐标算得出来，没必要多存一个字段占地方
    def center(self):# 定义 center 属性；把「算中心」这件事封装在 Box 内部，业务只管取，不用自己写一遍算式
        return (self.x + self.width // 2, self.y + self.height // 2)# 中心点 = 左上角 + 半个宽高；用整除 // 保证结果是整数像素，点击坐标不能带小数
 
    def relative_with_variance(self, rx=0.5, ry=0.5):# 定义「框内取点」；有些控件不能点正中（如带勾选框的选项要点左边），用相对比例就能精确指定
        # 按框内相对比例算实际坐标：rx=0.5 表示水平正中，ry=0.5 表示垂直正中
        return (self.x + int(self.width * rx), self.y + int(self.height * ry))# 按比例换算出真实像素坐标；rx/ry 用 0~1 表示，0.5 就是正中 —— 换分辨率时这个比例依然成立
 
    def crop_frame(self, frame):# 定义裁剪方法；把框内那一小块从大图抠出来做二次判断，先缩小范围再算能省下大量计算
        # 用这个框去裁剪大图，取出框内那一小块图像
        return frame[self.y:self.y+self.height, self.x:self.x+self.width]# numpy 切片取子图；行取 y 到 y+高、列取 x 到 x+宽，切片只是视图不复制数据，几乎没有开销
💡 为什么需要 relative_with_variance？ 有些按钮不能点正中心（比如带勾选框的选项，要点左侧的框）。rx/ry 让你指定「点框内哪个相对位置」，0.5 是正中，0.0 是左/上边缘。
✎ Feature vs Box 的关系： Feature 是「要找的模板图」，Box 是「找到后在哪、有多像」。一次匹配 = 拿 Feature 去匹配，产出一堆 Box。这两个类是整个识别层的「数据骨架」。

5 第 5 章 📸 后台截图：BitBlt 是怎么抓到最小化窗口的画面的

这是 ok-script 区别于普通脚本的第一个核心技术。普通截图（如 pyautogui）截的是「整个屏幕」，窗口最小化就抓不到。而 BitBlt 通过 Windows GDI，直接向窗口的绘图设备上下文（DC）请求画面，所以窗口即使被遮挡也能抓到。

💡 先理解三个 GDI 概念（看懂代码的前提）：
  • DC（设备上下文）：Windows 里「一块可绘制的画布」的句柄，窗口、屏幕各有一个
  • BitBlt：Block Bit Transfer，把一块 DC 的像素「位拷贝」到另一块 DC
  • Bitmap：内存里的一块像素缓冲区，用来接住拷出来的画面
Pythonok/device/capture_methods/bitblt.py（BitBltCaptureMethod 精简 + 逐行注释）
import threading# 导入线程模块；截图被放在独立线程里跑，不阻塞主逻辑，否则一边截图一边判断界面会卡成幻灯片
from ok.device.capture_methods.base import BaseWindowsCaptureMethod# 引入 Windows 截图基类；窗口句柄、裁剪点等公共逻辑直接复用，子类只写自己差异化的那一小段
from ok.device.capture_methods.bitblt_utils import capture_by_bitblt, composite_hwnds# 引入两个 GDI 工具函数：capture_by_bitblt 真正执行像素拷贝，composite_hwnds 把多个子窗口画面叠起来；把 GDI 细节关在工具函数里，本类只管流程
 
class BitBltCaptureMethod(BaseWindowsCaptureMethod):# 定义 BitBlt 截图类；继承基类后只需实现 do_get_frame 一个方法，就能接进框架的整套截图体系
    name = "BitBlt"# 类属性：截图方法名；配置界面靠它列出可选方式，字符串要和配置文件里写的保持一致
    short_description = "fastest, least compatible"# 一句取舍提示直接写在界面上；BitBlt 最快，但遇到硬件加速或独占全屏就可能抓不到 —— 让用户选之前就知道代价
 
    def __init__(self, hwnd_window):# 构造方法：接收目标窗口对象；后面所有截图都围绕这个窗口做，所以第一步先把它收进来
        super().__init__(hwnd_window)# 交给父类保存窗口对象；句柄、尺寸等由基类统一管理，避免每个子类各存一份、各改一套
        self.dc_object = None# 屏幕 DC 先占位；它代表「整个屏幕」这个拷贝源，等真正截图时再创建，省得长期占着 GDI 资源
        self.bitmap = None# 位图先占位；拷出来的像素要落在它里面，提前占位是为了在 close() 里能安全地按存在与否释放
        self.window_dc = None# 窗口 DC 先占位；它代表游戏窗口这个拷贝目标，也是「后台截图」的关键 —— 完全绕开屏幕本身
        self.compatible_dc = None# 兼容 DC 先占位；BitBlt 需要一块内存画布做中转，直接从屏幕 DC 拷到窗口 DC 在部分驱动上会失败
        self.lock = threading.Lock()# 建一把线程锁；GDI 对象不是线程安全的，截图线程和主线程同时操作它会直接把进程打崩
 
    def do_get_frame(self):# 实现子类必做的 do_get_frame；基类的 get_frame 负责判空、去 Alpha，这个方法只管「怎么把画面截出来」
        # with self.lock：加锁，防止多线程同时截图导致 GDI 崩溃
        with self.lock:# 进临界区加锁；保证同一时刻只有一个线程在操作 GDI 对象，这是避免原生层崩溃的硬性要求
            # 1. 算出要截的起点(x,y)和尺寸(width,height)
            x, y = get_crop_point(self.hwnd_window.window_width, self.hwnd_window.window_height,# 算出截取起点；窗口带边框和标题栏，先把它们排除掉，截出来的坐标才能和游戏内坐标对上
                                  self.hwnd_window.width, self.hwnd_window.height)# 续行：把目标窗口的截取尺寸一并传给上面这个函数；两行合起来才算一次完整调用
            width = self.hwnd_window.real_width or self.hwnd_window.width# 宽度优先取 real_width；窗口被缩放或 DPI 放大时它才是真实像素宽，取错会让截图整体变形
            height = self.hwnd_window.real_height or self.hwnd_window.height# 高度同理优先 real_height；用 or 兜底取不到就退回逻辑尺寸，保证尺寸永远拿得到、不会崩
            # 2. 核心一步：调用 win32 的 BitBlt，把窗口那块像素拷进 bitmap
            bg = capture_by_bitblt(self, self.hwnd_window.hwnd, width, height, x, y, render_full)# ★ 核心一步：调 BitBlt 把窗口那块像素拷进内存位图；全程不碰屏幕，所以窗口被遮挡甚至最小化也能截到
            # 3. 合成子窗口：游戏窗口可能由多个 hwnd 叠加（如悬浮 UI 层）
            bg = composite_hwnds(bg, self.hwnd_window, self.contexts, render_full)# 叠加子窗口画面；游戏的血条、公告这类悬浮 UI 常是独立 hwnd，不合成就只能截到残缺的画面
            return bg# 返回 numpy 数组；上层拿到的就是「一帧画面」，完全不用关心它是从屏幕、窗口还是内存里来的
 
    def close(self):# 定义 close()；GDI 对象必须显式释放，不调用会持续泄漏句柄，脚本跑久了系统变卡甚至直接崩
        # 释放所有 GDI 对象：不释放会和截图线程抢资源，导致原生层崩溃(access violation)
        with self.lock:# 释放时同样加锁；否则可能一边释放一边截图，资源被释放后还在用就变成野指针访问
            clean_up_bitblt(self)# 逐个释放 bitmap / DC 等 GDI 对象；释放顺序交给工具函数处理，避免漏掉某一个
            self.contexts.clear()# 清空子窗口上下文缓存；这些缓存里也握着 DC，不清理等于前面白释放了一场
✎ 为什么这是「后台」？ 注意整个过程没有调用 pyautogui、没有移动真实鼠标、也不需要窗口在前台——它只是向窗口的 DC 请求像素。所以游戏窗口可以被别的窗口盖住，甚至最小化（取决于渲染方式），照样能截图。
⚠️【BitBlt 的局限】 源码注释明确写了：OpenGL、硬件加速、独占全屏（Exclusive Fullscreen）的窗口，BitBlt 抓不到或抓到黑屏。因为这类窗口绕过了 GDI 直接写显存。遇到这种情况要换 DXGI 桌面复制（desktop_duplication.py）或前台截图。

5.1 🎨 截图基类：统一的「取一帧」接口

Pythonok/device/capture_methods/base.py（BaseCaptureMethod.get_frame）
def get_frame(self):# 定义统一入口 get_frame；所有截图方式对外都是这个签名，业务换后端时一行调用代码都不用改
    # 若收到退出信号，立即返回（让截图线程能优雅停止）
    if self.exit_event.is_set():# 先检查退出事件；截图线程常阻塞在等画面上，必须留一个随时能退出的检查点，否则关程序会卡住
        return# 收到退出信号就直接返回；上层看到 None 就结束循环，这就是「优雅停止」的落点
    try:# 用 try 包住整段流程；截图涉及大量 Win32 调用，异常五花八门，集中在一处处理比到处判断省心得多
        frame = self.do_get_frame()# 调子类真正的实现；基类定流程、子类填细节，这就是模板方法模式 —— 以后新增截图方式不用动基类
        if frame is not None:# 拿到帧才继续往下校验；截失败返回 None 是常态，先判空避免后面拿 None 去访问属性直接报错
            # 太小的图判为无效（宽高都≤10 说明没截到）
            if frame.shape[0] <= 10 or frame.shape[1] <= 10:# 尺寸过小直接判无效；窗口最小化或刚创建时经常返回几像素的残图，拿它去匹配只会产生一堆误报
                return None# 视为截图失败返回 None；让上层走「没截到」的分支，比返回一张垃圾图安全得多
            self._size = (frame.shape[1], frame.shape[0])# 记录帧尺寸（宽, 高）；后续把「图像坐标」映射回「窗口坐标」时要用到它
            # 若是 4 通道(BGRA)，砍掉 Alpha 只留 3 通道(BGR)
            if frame.shape[2] == 4:# 判断通道数；部分截图后端返回带 Alpha 的 BGRA 四通道，多出来的通道会干扰 OpenCV 匹配
                frame = frame[:, :, :3]# 切片砍掉 Alpha 只留 BGR；统一成三通道后，所有后端产出的帧格式一致，业务方不必再分情况处理
        return frame# 返回处理好的帧；到这里「判空、记尺寸、去 Alpha」这些共性问题都已由基类统一解决
    except Exception as e:# 捕获所有异常；截图失败的原因可能是句柄失效、驱动异常、超时，逐种去识别既没必要也不可靠
        raise CaptureException(str(e)) from e# 包装成自定义异常再抛出；from e 保留原始异常链方便追根因，上层也只需捕获一种异常类型
💡 模板方法模式： 基类 get_frame 定好「骨架流程」（检查退出→取帧→校验→去Alpha→返回），具体「取帧」交给子类 do_get_frame。这就是面向接口编程，业务只认 get_frame。

6 第 6 章 🖱️ 后台输入：PostMessage 怎么在后台点击

ok-script 的第二个核心技术。后台运行时，真实鼠标在用户手里（用户在用电脑干别的），不能真去动。解法是：绕过鼠标，直接向窗口句柄「投递」一条鼠标/键盘消息，游戏以为是它自己收到的点击。

💡 Windows 消息机制（先理解）： Windows 里所有操作都是「消息」。鼠标点击 = 系统给窗口发 WM_LBUTTONDOWN（左键按下）+ WM_LBUTTONUP（左键抬起）两条消息。PostMessage 就是「我直接往你窗口的消息队列塞一条消息」，游戏无从分辨这是真鼠标还是程序伪造的。
Pythonok/device/interaction_methods/post_message.py（PostMessageInteraction.click 精简 + 注释）
import win32gui, win32con, win32api# 引入 pywin32 三个模块；gui 负责发消息，con 提供 WM_* 消息常量，api 用来做虚拟键码到扫描码的转换
from ok.device.interaction_methods.base import BaseInteraction# 引入交互基类；日志、参数校验、点击前后的统一处理都在里面，子类只写自己不一样的部分
 
class PostMessageInteraction(BaseInteraction):# 定义「投递消息」式交互类；后台键鼠的核心思想就是「不产生真实动作，只往窗口消息队列塞消息」
    def click(self, x=-1, y=-1, move_back=False, name=None, down_time=0.01, move=True, key="left"):# 定义 click；x/y 默认 -1 表示沿用当前鼠标位置，key 决定左键还是右键，一个签名覆盖点击的常见变体
        super().click(x, y, name=name)# 先调父类钩子；日志、调试框、统计都在这里统一做，子类只管「怎么把消息发出去」这一件事
        # 1. 把游戏内坐标(x,y) 转成「窗口客户区坐标」，再打包成 lParam（一个32位整数）
        if move:# 判断是否先发移动消息；不少游戏只在收到鼠标移动后才更新内部光标位置，缺这一步点击会落空
            long_position = self.move(x, y)# 发一条移动消息并拿到打包好的坐标；先移后点更接近真人操作，命中率明显高于直接点
            time.sleep(down_time)# 移动后小停一下；紧接着发按下，部分游戏会来不及处理移动消息而把这次点击丢掉
        else:# 不移动鼠标的分支；只更新窗口内部记录的光标位置，适合不希望产生移动事件的场景
            long_position = self.update_mouse_pos(x, y, activate=True)# 做坐标转换并激活窗口；游戏内坐标要转成窗口客户区坐标，activate 顺带保证窗口处于可接收消息的状态
        # 2. 根据 key 选「按下/抬起」对应的消息常量
        if key == "left":# 按 key 选择消息常量；左键和右键用的是完全不同的 WM_* 消息，必须分开取
            btn_down, btn_up = win32con.WM_LBUTTONDOWN, win32con.WM_LBUTTONUP# 左键的「按下 / 抬起」消息；一次点击本质上就是这两条消息一前一后发出去
        else:# 其余情况按右键处理；框架目前只用到左右键，这样写足够且代码最短
            btn_down, btn_up = win32con.WM_RBUTTONDOWN, win32con.WM_RBUTTONUP# 右键的「按下 / 抬起」消息；换成右键只需换常量，其余流程完全复用
        # 3. 核心：投递「按下」消息，wParam 带上鼠标键状态位
        self.post(btn_down, win32con.MK_LBUTTON, long_position)# ★ 投递「按下」；wParam 带 MK_LBUTTON 是在告诉游戏「此刻左键处于按下状态」，缺了它拖拽会被识别成点击
        time.sleep(down_time)# 保持按下状态一小段时间；瞬间按下又抬起会被游戏当成无效抖动，down_time 就是留给它的余量
        # 4. 投递「抬起」消息，一次点击完成
        self.post(btn_up, 0, long_position)# 投递「抬起」；wParam 传 0 表示所有键都已释放，两条消息成对出现才算一次完整点击
 
    def post(self, message, wParam=0, lParam=0, hwnd=None):# 抽出统一的 post 方法；所有消息都从这一个出口发出，日志和异常处理只需写一遍
        # 真正干活的底层方法：调用 Win32 的 PostMessage 往消息队列塞消息
        if hwnd is None:# 允许临时指定别的窗口；默认用自己绑定的那个，需要给子窗口发消息时才显式传参
            hwnd = self.hwnd# 取构造时存下的窗口句柄；句柄就是这条消息的收件地址，填错就等于发给了别人
        try:# 加异常保护；消息发送偶尔会因句柄失效抛错，绝不能让一次点击失败炸掉整个任务
            win32gui.PostMessage(hwnd, message, wParam, lParam)# ★ 后台点击的灵魂；把消息直接塞进窗口的消息队列，不移动真实鼠标、窗口也不必在前台，用户还能继续用电脑
        except Exception as e:# 捕获发送异常；与上面的 try 配对成完整保护，异常不会继续往上冒
            logger.error(f'PostMessage error {hwnd}: {e}')# 记一条错误日志；带上句柄和原始错误，「点了没反应」时一看就知道是不是句柄过期了
✎ 坐标转换是难点（update_mouse_pos 干了什么）： 游戏给你的坐标是「截图内坐标」，但 PostMessage 需要「窗口客户区坐标」。所以要先 ClientToScreen 转屏幕坐标，再 ScreenToClient 转回目标窗口坐标，还要判断鼠标落在哪个子窗口句柄上——这套转换保证点击精确命中。
⚠️【后台输入的局限】 有些游戏会校验消息来源（检测 PostMessage 的特征），或用 DirectX 直接读鼠标硬件状态，这类游戏后台点击无效，只能退回「前台真实键鼠」（pydirect/pyautogui）。ok-script 提供了多种 interaction_methods 应对，配置里可切换。

PythonPostMessageInteraction.send_key（发一个按键）
def send_key(self, key, down_time=0.01):# 定义发送按键；一次按键 = 按下 + 停留 + 抬起，down_time 决定按住的时长
    super().send_key(key, down_time)# 调父类钩子记日志；父类内部带限流，长时间连按也不会把日志刷爆
    self.send_key_down(key)# 发 WM_KEYDOWN；把键名转成虚拟键码 VK 并打包 lParam，这一步才真正让游戏「收到按下」
    time.sleep(down_time)# 按住一小会儿再松；按住时长为 0 的按键很多游戏会当成无效输入直接忽略
    self.send_key_up(key)# 发 WM_KEYUP 松开；按键消息必须成对出现，只按下不抬起游戏会认为这个键一直被按住
 
# make_lparam 把「扫描码 + 按下/抬起标志」打包成 32 位整数，这是 Windows 键盘消息的格式要求
def make_lparam(self, vk_code, is_up=False):# 把键事件打包成 lParam；Windows 对键盘消息规定了固定的 32 位格式，格式不对游戏根本不认
    scan_code = win32api.MapVirtualKey(vk_code, 0)# 虚拟键码转扫描码；游戏引擎读的往往是硬件扫描码，只给 VK 有时收不到响应
    lparam = (scan_code << 16) | 1# 扫描码放高 16 位、最低位置 1；高 16 位是扫描码，最低位 1 表示「按下」，这就是消息的位布局约定
    if is_up:# 区分按下还是抬起；两种事件的标志位不同，靠这个参数让同一段打包逻辑服务两种场景
        lparam |= (1 << 30) | (1 << 31)# 抬起时额外置高两位；第 30 位是前一键状态、第 31 位是抬起标志，不置位游戏会把它理解成按下
    return lparam# 返回打包好的 lParam；交给 send_key_down / send_key_up 拼进消息里发给窗口

7 第 7 章 🎯 模板匹配：在大图里找出「最像」的那一块

这是识别层的算法核心。有了截图（大图）和 Feature（模板小图），怎么在大图里找到模板所在的位置？答案是 OpenCV 的 matchTemplate——让模板在大图上「滑动」，每滑到一个位置就算一个相似度分数，分数最高的地方就是匹配点。

Pythonok/feature/FeatureSet.py · find_one_feature（核心匹配逻辑精简 + 注释）
def find_one_feature(self, mat, category_name, ..., threshold=0, box=None, ...):# 定义核心匹配函数；mat 是要搜的大图，category_name 指定找哪个模板，threshold 和 box 用来控精度与范围
    if mat is None:# 先判大图是否为空；截图失败时后面所有计算都是白费，提前挡掉最省事
        return []# 返回空列表而不是 None；调用方统一按列表处理，少写一层判空分支，用的是调用方视角的设计
    if threshold == 0:# 阈值传 0 视为「没指定」；不用 None 判断是为了兼容配置文件传过来的 0 值，避免踩类型判断的坑
        threshold = self.default_threshold# 用默认阈值兜底（通常是 0.95）；让调用方可以一个参数都不传就用起来，降低上手门槛
    # 1. 取出模板图（若没直接给，就按名字从 feature_dict 里找）
    if template is None:# 没直接给模板图就按名字查；同一个函数既能「按名找」也能「按图找」，两种用法都覆盖得住
        feature = self.feature_dict[category_name]# 从特征字典取出 Feature 对象；字典查找是 O(1)，比每次遍历模板列表快得多
        template = feature.mat# 取出模板图像数组；下一步 matchTemplate 要的就是这个 numpy 数组
    # 2. 确定搜索范围：若给了 box，就只在这块区域里找（大幅提速 + 减少误匹配）
    if box is not None:# 给了搜索框就只在框内搜；全屏搜的耗时随像素数增长，限定范围往往能快好几倍
        search_x1 = max(box.x, 0); search_y1 = max(box.y, 0)# 左上角取 max(..., 0) 夹到非负；坐标可能是负的，不夹住切片会从数组尾部反向取值，结果全错
        search_x2 = min(box.x + box.width, mat.shape[1])# 右下角 x 夹到图宽以内；越界切片会得到比预期更小的区域，匹配结果直接失真
        search_y2 = min(box.y + box.height, mat.shape[0])# 右下角 y 同理夹到图高以内；这是保证后续切片合法的最后一道防线
    else:# 没给搜索框的分支；直接在整张图上搜，适合「不知道目标大致在哪个区域」的场景
        search_y2, search_x2 = mat.shape[:2]# 全图搜索的范围就是整张图；注意解包顺序是 (高, 宽)，要和 shape 的顺序对上
    # 3. 从大图里切出搜索区域（numpy 切片，不复制数据，很快）
    search_area = mat[search_y1:search_y2, search_x1:search_x2, :3]# 切出搜索区域；numpy 切片只是视图不复制数据，几乎不花时间，顺便还能砍掉多余通道
    # 4. ★ 核心：OpenCV 模板匹配，result 是一张「相似度热力图」
    result = cv2.matchTemplate(search_area, template, cv2.TM_CCOEFF_NORMED, mask=mask)# ★ 核心算法；模板在搜索区上逐格滑动、每格算一个相似度分数，输出一张热力图 —— 整个识别的算力都花在这一句上
    np.nan_to_num(result, copy=False, nan=0, posinf=0, neginf=0)# 把热力图里的 NaN / 无穷清成 0；纯色区域做归一化除法会算出非法值，不清理会污染后面的取峰值
    # 5. 只取最像的一个（limit==1）：拿最大值和阈值比
    boxes = []# 准备结果列表；下面「取一个」和「取多个」两个分支都往这个列表里塞，出口统一、调用方好处理
    if limit == 1 and match_method == cv2.TM_CCOEFF_NORMED:# 只要一个结果时走捷径；直接取全局最高分，比筛出所有候选点再挑更快
        min_val, max_val, min_loc, max_loc = cv2.minMaxLoc(result)# 一次遍历取出热力图最高分及其位置；max_loc 就是模板左上角在搜索区里的坐标
        if max_val >= threshold:# 分数达到阈值才算命中；设阈值是为了挡住「长得有点像」的假目标，0.95 是很常见的取值
            x, y = round(max_loc[0] / scale_factor) + search_x1, round(max_loc[1] / scale_factor) + search_y1# 换算回真实坐标；搜索是在缩放图上做的，要先除以缩放系数，再加上搜索区的偏移
            boxes.append(Box(x, y, feature_width, feature_height, max_val, category_name))# 生成 Box 作为结果；置信度直接带上 max_val，业务可以据此再决定要不要信这次匹配
    else:# 要找多个结果的分支；例如「把所有相同按钮都找出来」就需要这一路
        # 找所有超过阈值的点（如找全部相同按钮），并做非极大值抑制去重
        locations = filter_and_sort_matches(result, threshold, template.shape[1], template.shape[0])# 筛出所有超过阈值的点并排序；配合非极大值抑制，避免同一个目标被重复报好几次
        for loc in locations:# 遍历每个候选位置；每个候选都要换算坐标并生成各自的 Box
            x, y = round(loc[0][0] / scale_factor) + search_x1, round(loc[0][1] / scale_factor) + search_y1# 与单结果分支相同的坐标还原；loc[0] 是位置、loc[1] 是该点的分数
            boxes.append(Box(x, y, feature_width, feature_height, loc[1], category_name))# 追加一个 Box；每个候选点保留自己的置信度，方便业务按分数再过滤
        boxes = sort_boxes(boxes)# 按位置统一排序；顺序稳定后业务取「第几个按钮」才不会每帧结果都在变
    return boxes# 返回 Box 列表；统一返回列表（哪怕只有一个）能让调用方少写一套分支
💡 TM_CCOEFF_NORMED 是什么？ 这是归一化相关系数匹配法，结果范围 -1~1。1 表示完全相同，0 表示毫不相关，负数表示「反相」（颜色互补）。所以阈值一般设 0.9 以上。它抗亮度变化，是游戏匹配最常用的方法。

8 第 8 章 🧩 BaseTask：把底层能力封装成「业务能用的积木」

前面几章拆的是「底层零件」。但业务开发者不该直接碰 BitBlt、PostMessage、matchTemplate——太繁琐。ok-script 用 BaseTask 把这些全封装好，你写业务时只需调 click / send_key / find_feature 这些「高层动作」。

Pythonok/task/task.py · click_box（「找到框并点击」的高层封装）
def click_box(self, box=None, relative_x=0.5, relative_y=0.5,# 高层封装：给一个框或一个名字就自动算出坐标并点击；业务一行调用，背后把截图、找图、点击全做完

        self.logger.error(f"click_box box is None")# 先记一条错误日志；脚本静默失败最难查，日志里留下线索是排查的第一步
        if raise_if_not_found:# 由调用方决定「找不到」算不算错误；日常任务里找不到很常见，不一定该中断整个流程
            raise Exception(f"click_box box is None")# 需要严格时抛出异常；让上层能收到明确的失败信号，而不是带着错误状态继续往下跑
        return# 否则安静返回；让函数行为可预期，调用方不做异常处理也能安全继续
    # 算出框内相对坐标（默认正中 0.5,0.5），再调底层 click
    x, y = box.relative_with_variance(relative_x, relative_y)# 算出框内实际点击点；默认点正中，需要点边角（如勾选框）时改 relative_x / relative_y 即可
    return self.click(x, y, name=box.name, move_back=move_back, move=move,# 交给底层 click 真正投递消息；坐标已算好，这里只负责透传参数，职责边界清楚
                          down_time=down_time, after_sleep=after_sleep)# 透传剩余参数；让调用方能穿透控制按下时长和点击后的等待，不用为此层层修改方法签名
💡 BaseTask 提供的「积木」（部分）：
方法作用（重点方法）
click / click_box点击坐标 / 点击识别到的框
send_key / send_key_down/up发一个按键 / 按下 / 抬起

✎ 分层封装的价值： 业务代码写 self.click_box("confirm_btn") 一行，背后自动完成「截图→找confirm_btn→算坐标→PostMessage点击→等待」。底层多复杂都被藏起来了——这就是框架的意义，也是你学设计时代码要追求的目标。

9 第 9 章 🔄 串起来：一句 click_box 背后发生了什么

现在把前 8 章的零件全串起来。当你在业务里写下 self.click_box("confirm_btn")，框架内部是这样一条流水线：

① 触发截图

BaseTask 调 capture.get_frame() → BitBlt 向游戏窗口 DC 请求像素，返回一帧 numpy 数组

② 取出模板

按名字 confirm_btn 从 FeatureSet.feature_dict 取出 Feature → 拿到模板图数组和它的坐标

③ 模板匹配

find_one_feature → cv2.matchTemplate 在大图里滑窗，算出相似度热力图，取峰值

④ 判定 + 定位

峰值 max_val >= threshold？→ 是则生成 Box(坐标, 置信度)，否则返回空（没找到）

⑤ 算点击点

box.relative_with_variance(0.5,0.5) → 算出框正中心的屏幕坐标

⑥ 后台点击

interaction.click(x,y) → 坐标转窗口客户区坐标，PostMessage 投递 WM_LBUTTONDOWN + WM_LBUTTONUP

⑦ 等待

after_sleep=1 → 睡 1 秒等界面响应，然后整个循环再来一遍（找下一个目标）

✎ 看懂这张图，你就看懂了 ok-script： 所谓「游戏自动化框架」，就是把上面这条流水线封装得足够好用、足够稳（后台、多分辨率、多线程、调试浮层都是围绕它做的增强）。所有复杂功能，剥开都是这个循环。

10 第 10 章 ✍️ 实战：基于框架，你自己能写出什么样的任务

理解了原理后，写业务其实很短。下面是一个「自动领取日常奖励」任务的示意代码——它调用的全是上面解析过的 BaseTask 方法：

Python你的第一个 ok-script 任务（示意，基于 BaseTask API）
from ok import og# 从框架取出全局入口 og；它是任务、设备、配置的统一挂载点，后面的 og.task.BaseTask 就来自这里
 
# 继承 BaseTask：白嫖 click/send_key/wait_scene 等全部能力
class DailyRewardTask(og.task.BaseTask):# 继承 BaseTask；截图、找图、点击、等待这些能力全都现成，业务只需表达「什么情况下点哪里」
    # 定义这个任务要用的模板图集合（对应 coco.json 里的标注）
    feature_set_names = ["daily_ui"]# 声明用到的模板集合；框架据此只加载这一组模板图，既省内存也让匹配范围更聚焦
 
    # 主逻辑：框架会反复调用 run，直到任务完成或退出
    def run(self):# 实现 run 方法；框架会反复调用它，每次调用相当于「看一眼当前界面，只做一件事」
        # 场景1：在主界面 → 点「日常」入口
        if self.click_box_if_name_match(self.find_feature("daily_entry"), "daily_entry"):# 找到并点击「日常」入口；find_feature 负责找、click_box_if_name_match 负责确认名字后点击，一句顶三步
            self.sleep(1)# 点完必须等界面加载；切界面有动画和网络请求，立刻截图只会截到旧画面导致误判
            return# 做完一件事立刻 return；让框架下一帧重新截图判断，而不是在同一帧上连续操作，逻辑才稳
        # 场景2：在日常面板 → 逐个领取奖励
        if self.click_box_if_name_match(self.find_feature("claim_btn"), "claim_btn"):# 在奖励面板里找「领取」按钮并点击；奖励可能有好几个，每帧领一个、靠循环自然轮询
            self.sleep(0.5)# 领奖后短暂等待；留出动画和服务器返回的时间，避免连点被限流或漏掉下一个按钮
            return# 同样先 return；一次 run 只处理一个动作，界面推进交给后续帧
        # 场景3：领完了 → 点关闭
        if self.click_box_if_name_match(self.find_feature("close_btn"), "close_btn"):# 面板里没有可领的了就点关闭；用「先领后关」的优先级，保证不会漏领就退出
            self.stop()# 通知框架结束任务；stop 比 return 更彻底，它会终止整个 run 循环而不是只结束当前这一帧
            return# 顺手 return；stop 之后不该再执行后面的兜底逻辑
        # 都没匹配到：说明界面没按预期走，返回主界面重试
        self.send_key("esc")# 兜底按 ESC 回退；三种情况都不匹配说明界面跑偏了（弹窗、掉线等），退回上一层下一帧再判断
💡 这段代码的精髓——「状态机」思想： 游戏界面是「状态」，每次截图识别出「当前在哪个状态」，就执行对应动作。run 被反复调用，界面一步步推进，直到完成。这就是所有游戏日常脚本的通用写法。
⚠️【真实项目的 70% 工作量在这】 代码框架就这么点，真正耗时的是：① 截大量模板图（每个按钮、每个界面）② 调阈值和搜索区 ③ 处理各种异常界面分支 ④ 多分辨率适配。这些是「脏活」，但理解了原理你都能搞定。
